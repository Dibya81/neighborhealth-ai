# NeighborHealth 2.0

**Dengue early warning for Bengaluru, built on real government surveillance data, with honest uncertainty.**

NeighborHealth turns the Karnataka health department's daily dengue bulletins (a PDF per day) into a weekly
case series for BBMP, forecasts the next 1–4 weeks with calibrated prediction ranges, estimates ward-level
risk, and gives residents and health officials tools to act on it: photo-checked citizen reports, alerts in
English, Kannada and Hindi, a guideline-grounded assistant, and an officials' dashboard with inspection routing.

> **Read this first: data status.** The public bulletin archive ends on **2024-11-04**, so every forecast this repository
> can produce today describes **November 2024**, not now. The system says so (`/health` reports `degraded`) and the alert engine
> refuses to send anything from a forecast older than 21 days. Use it for demos, research and pilot preparation until a live data
> source is connected. See [Limitations](#limitations-and-roadmap).

## Why v2 exists

The first version (v1) had a sound structure but its machine learning was not real: case counts, community reports and the
outbreak label were generated by a hand-written formula of rain, temperature, humidity, month and density, and the model was trained
on those same inputs. Its reported ROC-AUC of 0.986 measured how well it copied the formula, not anything about dengue. Early stopping and
the decision threshold were also tuned on the test set.

v2 throws that data away and starts from real surveillance data, with a pipeline whose accuracy is measured:

- **No synthetic data.** v1's synthetic files are not read or committed. Only real inputs are tracked (bulletins, NASA POWER weather, Census 2011 wards).
- **Leakage-free evaluation.** Rolling-origin backtests, features built only from information available at the forecast date, intervals built only from past errors.
- **v1 is preserved.** The original README, with its live demo link, is kept at [docs/v1/README.md](docs/v1/README.md); the v1 code stays in `backend/` and `frontend/` for reference.
- **Honest claims.** Every number in this README comes from a check you can re-run; results that are unflattering are reported as such.

## What was measured

### Data extraction (real bulletins, no hand labels needed)

| Check | Result |
|---|---|
| Archive coverage | 606 bulletins, 2021-09-29 → 2024-11-04 (nothing before or after) |
| Text bulletins whose 30+ district rows sum **exactly** to the printed state total | **374 of 379 (98.7%)** |
| Scanned bulletins (Oct 2023 on) with a BBMP value read by OCR and arithmetic-checked | 129 of 165; most of the rest are genuinely blank rows |
| Rebuilt Karnataka totals vs the Ministry's separate annual table | 2021: 100% · 2022: 98% · 2024 (to 4 Nov): 95% · **2023: 87%** (see data card) |
| Weekly BBMP series | 161 weeks (2021-10 → 2024-11-03); 113 backed by ≥3 real bulletins; Apr–May 2023 is a gap in the archive itself |

### Forecast skill (rolling backtest, scored only on weeks with real observations; 48 weeks)

| Horizon | Ensemble MAE | Seasonal-naive MAE | Skill vs seasonal naive | 80% interval coverage |
|---|---|---|---|---|
| 1 week | 208 | 241 | **+13.6%** | 0.83 |
| 2 weeks | 237 | 241 | +1.7% | 0.80 |
| 3 weeks | 253 | 241 | −4.7% | 0.79 |
| 4 weeks | 258 | 241 | −7.2% | 0.87 |

The model helps one week ahead and not beyond. Averaged over horizons the skill is within ±0.01 of zero, so whether the quality gate promotes a
model depends on how often models are refit. With only 161 weeks of real data this is a finding about the data, not a bug. Intervals are roughly calibrated
but wide (for example roughly 3–756 reported cases for the next week at 80%).

## Architecture

```

        │                                                  │                          │
        ▼                                                  ▼                          │
 pipeline/  download → parse text / OCR scans → validate → reconcile → weekly series  │
        │                                                                              ▼
        ▼
 ml/   6 models → rolling backtest → conformal intervals → SHAP → ward allocation
        │     → registry + quality gate → publish latest.json (+ drift report, model card)
        ▼
 apps/api (FastAPI)  forecast · wards · reports · officials · alerts · assistant · privacy · pilot
        │                    │                           │
   SQLite / Postgres   Redis Streams → worker → email / SMS / WhatsApp
        │
 apps/web (Next.js)  residents and health team
```

## Quick start

**Requirements:** Python 3.11+ (developed on 3.14), Node 20 for the web app, Docker optional. **OCR of scanned bulletins needs macOS**
(Apple Vision); everything else runs on Linux and macOS, and the OCR output is committed so other machines don't need to repeat it.

```bash
git clone https://github.com/Dibya81/neighborhealth-ai.git && cd neighborhealth-ai
git checkout v2
python3 -m venv .venv && source .venv/bin/activate
pip install -r apps/api/requirements.txt          # pipeline + ML + API
cp apps/api/.env.example apps/api/.env            # then edit (JWT secret, optional keys)
```

### 1. Use the committed real dataset (no download)

The weekly series and extracted bulletins are in the repository, so you can go straight to the forecast:

```bash
export PYTHONPATH=$PWD:$PWD/apps/api
python -m ml weekly --no-download                # backtest all models, gate, publish the forecast (a few minutes)
cd apps/api
python -m app.services.assistant.corpus fetch    # downloads WHO + NCVBDC guidelines, builds the search index
python -m app.services.clinics fetch             # nearby hospitals from OpenStreetMap
cd ../..
```

### 2. Rebuild the data from the source (optional)

```bash
make data          # download bulletins + weather, extract (text + OCR), build the weekly series
python -m pipeline status
```
The downloader is polite (1 request/second), resumable, and records every missing date in a manifest. Raw PDFs (about 300 MB) are not committed.

### 3. Run the API and worker

```bash
make api                                          # http://localhost:8000/docs
make worker                                       # alert delivery (dry-run: writes data/v2/outbox.log)
make officials EMAIL=you@example.org PASSWORD=choose-a-password
```
If port 8000 is taken: `cd apps/api && uvicorn app.main:app --port 8010`.

### 4. Everything in containers

```bash
docker compose up --build
docker compose run --rm api python -m ml weekly --no-download     # the data volume is seeded with the real series on first start
docker compose run --rm api python -m app.services.assistant.corpus fetch
```

### 5. Tests

```bash
make test        # pipeline + ML + API  (~40 s)
make lint
```

### 6. Web app

```bash
cd apps/web && npm install
NEXT_PUBLIC_API_URL=http://localhost:8000 npx next dev -p 3100   # http://localhost:3100
npm run typecheck && npm run build
```
Set `ALLOWED_ORIGINS` on the API to the web address (for example `http://localhost:3100`).

## How it works

**Reading the bulletins.** Real bulletins leave cells blank (the whole "on the day" block on most rows), so numbers are assigned to columns
by *position* (measured from the always-complete Total row), not by counting. Scanned bulletins (from Oct 2023) are deskewed, orientation-corrected, and the BBMP and
Total rows are read by OCR several times; a reading is accepted only if IgM + NS1 = Total and Total ≤ Samples ≤ Suspected.

**Weekly series.** Weekly cases are differences of the year-to-date cumulative at consecutive Sundays, so missing days don't lose cases.
Each week records how many real bulletins it contains; **interpolated weeks are never used to score models**.

**Forecasting.** Persistence, seasonal naive, SARIMA with Fourier terms, Poisson GLM, gradient boosting and an ensemble; rolling-origin backtests
for horizons 1–4; online conformal 50/80/95% intervals; WIS and coverage; SHAP drivers grouped into readable factors. A challenger replaces the champion only if
it passes the quality gate (beats seasonal naive on MAE, 80% coverage in 0.65–0.95) and is at least as good on the same data.

**Ward risk** is an allocation of the city forecast by estimated population and risk factors with Monte Carlo uncertainty. It is a model estimate, never an observed ward count, and is labelled so.

## Safety and privacy

- **Not medical advice.** The assistant never diagnoses. Warning signs of severe dengue (English, Kannada, Hindi) trigger an urgent message with **108** and the three nearest hospitals before anything else.
- **Answers only from official guidelines**, with citations; out-of-scope questions are refused rather than answered from a random passage.
- **No alerts from old data.** The alert engine refuses to run when the forecast data is older than 21 days; delivery is dry-run until you switch it off.
- **Opting out works.** Email alerts carry a signed one-click unsubscribe link; replying STOP to an SMS/WhatsApp alert is handled by a signature-verified Twilio webhook.
- **Your data, your call.** `GET /v2/auth/me/export` and `DELETE /v2/auth/me` (password re-checked). Photos have EXIF stripped; names and photos are never shown publicly.
- **Honest limits:** faces and number plates are *not* blurred automatically; there is no automatic retention rule yet. Drafts: [privacy notice](docs/v2/legal/PRIVACY_NOTICE.md), [terms](docs/v2/legal/TERMS.md).

## Configuration

City-specific settings (location, thresholds, routing) live in `config/cities/bengaluru.yaml`. Secrets and switches are environment variables (see `apps/api/.env.example`):

| Variable | Purpose |
|---|---|
| `APP_ENV` | `production` refuses to start with the default `JWT_SECRET` |
| `JWT_SECRET` | Token signing key (also signs unsubscribe links) |
| `DATABASE_URL` / `REDIS_URL` | SQLite by default; Postgres + PostGIS and Redis in containers |
| `ALLOWED_ORIGINS`, `PUBLIC_WEB_URL`, `PUBLIC_API_URL` | CORS, alert links, unsubscribe links, Twilio signature check |
| `ALERTS_DRY_RUN` | `true` writes messages to `data/v2/outbox.log` instead of sending |
| `OPENROUTER_API_KEY` | Optional: LLM answers and PDF extraction cross-check; without it the assistant shows the best official passages verbatim |
| `TWILIO_*`, `SMTP_*` | Delivery credentials |
| `VISION_ENABLED` | Optional zero-shot photo check (large download) |

## Testing and CI

`make test` runs pipeline, ML and API tests (including regression tests built from real bulletins and a test that account deletion leaves other people's data intact).
GitHub Actions (`.github/workflows/ci.yml`) runs lint, the tests, a model quality gate (when a registry is present) and the web build (non-blocking until the UI pass).
The weekly retrain workflow is **disabled on purpose** until a live data source exists.

## Limitations and roadmap

**Known limitations**
- Data ends 2024-11-04; the 2023 bulletin totals are about 13% below the Ministry's annual figure.
- 161 weeks is little history; forecasts beat the baseline only one week ahead.
- Ward values are allocations, and 2011 population is an approximation.
- Keyword-only retrieval in the assistant; held-out recall is about 50%.
- No automated UI tests; Kannada/Hindi unreviewed; no automatic photo blurring; per-process rate limiting; token in `localStorage`.

**Next**
1. A live data source (district/state weekly reports such as IDSP, or a new ICTS feed) so forecasts and alerts can be current.
2. Automated UI tests (Playwright) and a real-user usability check of the report and alert flows.
3. Embeddings + reranker for the assistant and a larger evaluation set.
4. Probabilistic outbreak alerts (P(next week > seasonal 75th percentile)) scored with the Brier score.
5. Deploy, privacy review, and a small pilot with one RWA or NSS unit ([playbook](docs/v2/PILOT_PLAYBOOK.md)).
